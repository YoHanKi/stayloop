# 블로그 다듬기 스킬

> 초안에서 AI 티 나는 표현을 빼고 사람 말투로 다듬는 가이드. 글을 다 쓴 뒤 마지막 단계에서 적용한다.

---

## 0. 핵심 원칙

AI가 쓴 글은 **문장이 짧게 끊어진다.** 사람이 쓴 글은 **자연스럽게 이어진다.**

```
AI: "이메일 검증을 한 곳에 모았다. 어디서든 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다."

사람: "이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 
       컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다."
```

가장 중요한 다듬기는 **짧은 문장을 자연스럽게 연결하는 것**이다.

---

## 1. 짧은 문장 → 자연스러운 연결

AI는 "~다. ~다. ~다." 패턴을 자주 쓴다. 이걸 연결어미로 묶는다.

### 변환 패턴

| 끊어진 문장 | 자연스럽게 이은 문장 |
|---|---|
| "~다. 그런데 ~다." | "~지만 ~다" / "~인데 ~다" |
| "~다. 그래서 ~다." | "~기 때문에 ~다" / "~니까 ~다" |
| "~다. 또한 ~다." | "~이고, ~다" |
| "~다. 즉 ~다." | "~인 셈이다" |
| "~다. 결국 ~다." | "~다 보니 ~다" |

### 자주 쓰는 연결어미

* **"~인데"** : 부드러운 전환
* **"~기 때문에"** : 명확한 인과
* **"~지만"** : 대조
* **"~서"** : 짧은 인과
* **"~니"** / "~니까" : 자연스러운 인과
* **"~다 보니"** : 결과 도출
* **"~ㄴ 셈이다"** : 결론 풀이

### 변환 예시

**Before**:
```
VO 는 답이었다. 정확히는, 답인 줄 알았다.
이메일 검증을 한 곳에 모았다. 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다.
```

**After**:
```
VO 를 도입하면 어떻게 될까?
이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 
컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다.
```

## 2. AI가 자주 쓰는 표현 빼기

### 감정 표현

| AI 표현 | 다듬은 표현 |
|---|---|
| "거슬렸다" | "문제가 보였다" / "어색했다" / 빼기 |
| "어색해졌다" | "번거로워졌다" / "복잡해졌다" |
| "안타깝게도" | 빼기 |
| "흥미롭게도" | 빼기 |
| "놀랍게도" | 빼기 |
| "정확히는, ~인 줄 알았다" | "~한 줄 알았다" |

### 회고 감성

| AI 표현 | 다듬은 표현 |
|---|---|
| "이게 가장 뒤늦게 깨달은 것이다" | 빼고 본론 바로 시작 |
| "결국 알게 된 것은" | "정리하면" |
| "돌이켜보면" | 빼기 |
| "~을 깨달았다" | "~을 알게 됐다" / "~인 것을 알았다" |
| "원칙을 정했다" | "기준은 단순하다" |

### 명사화 과다

AI는 "~라는 사실이다" "~라는 의미다" 같은 명사화를 자주 쓴다. 이걸 풀어준다.

| AI 표현 | 다듬은 표현 |
|---|---|
| "~라는 사실이다" | "~다" |
| "~라는 의미다" | "~는 뜻이다" |
| "~게 된다는 것이다" | "~게 된다" |
| "~인 셈인 것이다" | "~인 셈이다" |
| "비대칭이 생긴다는 것이다" | "비대칭이 생긴다" |

### 극적 장치

| AI 표현 | 다듬은 표현 |
|---|---|
| "그런데 그게 다가 아니었다" | 빼기 |
| "여기서 흥미로운 일이 벌어진다" | 빼기 |
| "충격적이게도" | 빼기 |
| "~의 정체는 무엇이었을까" | 자연스럽게 본론으로 |

## 3. 같은 의미 반복 빼기

AI는 같은 말을 다른 표현으로 두 번 한다.

### 예시

**Before**:
```
VO 는 검증을 위한 것이 아니다. 그것은 값에 이름을 주기 위한 것이다.
검증은 그 이름이 데려오는 부수 효과의 일부일 뿐이다.
```

**After**:
```
VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이다.
```

같은 의미를 두 번 하면 한 번만 한다.

---

## 4. "~합니다" vs "~다" 통일

요한의 글은 **평어체 ("~다") 가 기본**이다. 정중체와 섞이면 어색하다.

### 변환 예시

| 정중체 | 평어체 |
|---|---|
| "~했습니다" | "~했다" |
| "~합니다" | "~한다" |
| "~이었습니다" | "~이었다" |
| "~할 수 있습니다" | "~할 수 있다" |
| "~지 않을까요" | "~지 않을까" |

다만 **글 전체 톤을 평어체로 통일**하기로 정했다면 일관되게 적용해야 한다.

## 5. 챕터 마무리 다듬기

AI는 챕터를 "그래서 다음 장에서는 ~을 살펴보겠다" 같은 메타 문장으로 끝낸다. 이걸 **자연스러운 의문문**으로 바꾼다.

### 변환 패턴

**Before**:
```
이렇게 VO + Converter 방식의 한계를 살펴봤다.
다음 장에서는 다른 접근법을 알아보겠다.
```

**After**:
```
VO 를 늘릴수록 Converter 도 함께 늘어난다. 또 다른 방법은 없을까?
```

---

## 6. 도입부 다듬기

AI는 도입부에 **"이 글에서는 ~을 다룰 것이다"** 같은 메타 설명을 넣는다. 이걸 빼고 바로 본론으로 들어간다.

### 빼야 할 도입부 패턴

* "이 글에서는 ~에 대해 알아보자"
* "오늘은 ~에 대해 정리해보려고 한다"
* "최근 ~을 고민하다가 ~을 알게 됐다. 그 과정을 정리한다"
* "같은 질문을 세 번째 받고 있다..." (감성 도입부)

### 좋은 도입

TL;DR 다음에 바로 1장 코드부터 시작하거나, 한 줄짜리 화두만 던지고 들어간다.

---

## 7. 마지막 잠언 다듬기

마지막 잠언은 **짧고 단정적**이어야 한다.

### Before (늘어지는)

```
세 번의 답을 거치면서 정리된 것은 이렇다... (본문)

VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이었다. 
검증은 그 이름이 데려오는 부수 효과의 일부일 뿐이었다.

다음 프로젝트에서 또 같은 질문 앞에 서면, 답이 또 달라질지도 모른다. 
그땐 그때의 거슬림을 또 정리하면 된다.
```

### After (짧고 단정적)

```
세 번의 답을 거치면서 정리된 것은 이렇다... (본문)

***VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이다.***
```

* "~이었다" 과거형 → "~이다" 현재형
* 늘어지는 후일담 빼기
* 굵게 + 기울임으로 시각적 마무리

## 8. 강조 장치 정리

### 줄여야 할 강조

* 따옴표 강조 ("정말로", "사실은") — AI 티
* 말줄임표 (...) — 거의 안 씀
* 굵은 글씨 남발 — 한 문단에 한두 개만
* 이모지 / 느낌표 — 사용 안 함

### 적절한 강조

* **굵은 글씨** : 핵심 개념 한 단어 또는 짧은 구절
* `코드 인라인` : 변수명, 클래스명, 키워드
* > 인용구 : 핵심 원칙, 잠언

## 9. 다듬기 체크리스트

초안을 다 쓴 뒤 다음을 확인한다.

### 문장 차원

- [ ] "~다. ~다. ~다." 짧은 문장이 3개 이상 연속되지 않는가?
- [ ] "~지만", "~기 때문에", "~인데" 같은 연결어미를 쓰고 있는가?
- [ ] 같은 의미를 두 번 반복한 부분이 없는가?

### 단어 차원

- [ ] "거슬렸다", "어색해졌다" 같은 감정 표현이 과다하지 않은가?
- [ ] "~라는 사실이다", "~라는 의미다" 같은 명사화가 과다하지 않은가?
- [ ] "흥미롭게도", "안타깝게도" 같은 부사가 들어 있지 않은가?

### 구조 차원

- [ ] 도입부에 "이 글에서는 ~" 같은 메타 설명이 있지 않은가?
- [ ] 챕터 마무리가 자연스러운 의문문 또는 결론으로 끝나는가?
- [ ] 마지막 잠언이 짧고 단정적인가?
- [ ] 정중체와 평어체가 섞이지 않았는가?

### 톤 차원

- [ ] 한 문단이 너무 길지 않은가? (4문장 넘으면 의심)
- [ ] 추상적 원칙만 있고 구체적 코드/사례가 없는 챕터가 있지 않은가?
- [ ] 굵은 글씨가 한 문단에 너무 많이 들어가지 않았는가?

## 10. 변환 작업 우선순위

다듬을 때 시간 없으면 이 순서로:

1. **짧은 문장 연결** (가장 큰 효과) — 1번 항목
2. **AI 감정 표현 제거** — 2번 항목
3. **"~합니다" / "~다" 통일** — 4번 항목
4. **마지막 잠언 다듬기** — 7번 항목
5. **챕터 마무리 자연스럽게** — 5번 항목

이 다섯 가지만 챙겨도 80%의 AI 티는 사라진다.

## 11. 변환 예시 모음

실제 변환 사례를 모아둔다. 비슷한 패턴을 만나면 참고한다.

### 사례 A: 끊어진 문장 → 이어진 문장

**Before**:
> VO 는 답이었다. 정확히는, 답인 줄 알았다. 이메일 검증을 한 곳에 모았다. 어디서 이메일을 만들든 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다. 타입 자체가 검증된 사실을 보장한다.

**After**:
> VO 를 도입하면 어떻게 될까? 이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다.

### 사례 B: AI 감정 표현 제거

**Before**:
> 여기까지는 좋았다. 그런데 코드를 더 짜다 보니 거슬리는 자리들이 줄줄이 나왔다.

**After**:
> 여기까지는 좋았는데, 코드를 더 짜다 보니 몇 가지 문제가 보이기 시작했다.

### 사례 C: 명사화 풀어주기

**Before**:
> VO 가 가진 "항상 유효함" 보장이 nullable 자리에 들어가는 순간 비대칭이 생긴다는 것이다.

**After**:
> 원시 타입이었다면 한 줄로 끝날 일이 세 줄이 되어버리는 셈이다.

(같은 의미인데 더 구체적이고 짧게)

**Before**:
```
같은 질문을 세 번째 받고 있다. 새 프로젝트에서 회원 도메인을 다시 짜면서, 
이메일과 전화번호와 비밀번호를 손에 쥐고 또 멈춰 섰다.

답은 매번 달랐다. 그리고 매번 어딘가가 거슬렸다. 
이번엔 그 거슬림의 정체를 정리해두려 한다.

---

## 1. String 원시타입
```

**After**:
```
## 1. String 원시타입
```

# 블로그 다듬기 스킬

> 초안에서 AI 티 나는 표현을 빼고 사람 말투로 다듬는 가이드. 글을 다 쓴 뒤 마지막 단계에서 적용한다.

---

## 0. 핵심 원칙

AI가 쓴 글은 **문장이 짧게 끊어진다.** 사람이 쓴 글은 **자연스럽게 이어진다.**

```
AI: "이메일 검증을 한 곳에 모았다. 어디서든 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다."

사람: "이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 
       컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다."
```

가장 중요한 다듬기는 **짧은 문장을 자연스럽게 연결하는 것**이다.

---

## 1. 짧은 문장 → 자연스러운 연결

AI는 "~다. ~다. ~다." 패턴을 자주 쓴다. 이걸 연결어미로 묶는다.

### 변환 패턴

| 끊어진 문장 | 자연스럽게 이은 문장 |
|---|---|
| "~다. 그런데 ~다." | "~지만 ~다" / "~인데 ~다" |
| "~다. 그래서 ~다." | "~기 때문에 ~다" / "~니까 ~다" |
| "~다. 또한 ~다." | "~이고, ~다" |
| "~다. 즉 ~다." | "~인 셈이다" |
| "~다. 결국 ~다." | "~다 보니 ~다" |

### 자주 쓰는 연결어미

* **"~인데"** : 부드러운 전환
* **"~기 때문에"** : 명확한 인과
* **"~지만"** : 대조
* **"~서"** : 짧은 인과
* **"~니"** / "~니까" : 자연스러운 인과
* **"~다 보니"** : 결과 도출
* **"~ㄴ 셈이다"** : 결론 풀이

### 변환 예시

**Before**:
```
VO 는 답이었다. 정확히는, 답인 줄 알았다.
이메일 검증을 한 곳에 모았다. 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다.
```

**After**:
```
VO 를 도입하면 어떻게 될까?
이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 
컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다.
```

## 2. AI가 자주 쓰는 표현 빼기

### 감정 표현

| AI 표현 | 다듬은 표현 |
|---|---|
| "거슬렸다" | "문제가 보였다" / "어색했다" / 빼기 |
| "어색해졌다" | "번거로워졌다" / "복잡해졌다" |
| "안타깝게도" | 빼기 |
| "흥미롭게도" | 빼기 |
| "놀랍게도" | 빼기 |
| "정확히는, ~인 줄 알았다" | "~한 줄 알았다" |

### 회고 감성

| AI 표현 | 다듬은 표현 |
|---|---|
| "이게 가장 뒤늦게 깨달은 것이다" | 빼고 본론 바로 시작 |
| "결국 알게 된 것은" | "정리하면" |
| "돌이켜보면" | 빼기 |
| "~을 깨달았다" | "~을 알게 됐다" / "~인 것을 알았다" |
| "원칙을 정했다" | "기준은 단순하다" |

### 명사화 과다

AI는 "~라는 사실이다" "~라는 의미다" 같은 명사화를 자주 쓴다. 이걸 풀어준다.

| AI 표현 | 다듬은 표현 |
|---|---|
| "~라는 사실이다" | "~다" |
| "~라는 의미다" | "~는 뜻이다" |
| "~게 된다는 것이다" | "~게 된다" |
| "~인 셈인 것이다" | "~인 셈이다" |
| "비대칭이 생긴다는 것이다" | "비대칭이 생긴다" |

### 극적 장치

| AI 표현 | 다듬은 표현 |
|---|---|
| "그런데 그게 다가 아니었다" | 빼기 |
| "여기서 흥미로운 일이 벌어진다" | 빼기 |
| "충격적이게도" | 빼기 |
| "~의 정체는 무엇이었을까" | 자연스럽게 본론으로 |

## 3. 단정 톤 → 경험적 결론 톤

AI는 결론을 **"이게 정답이다"** 처럼 단정적으로 적는다. 하지만 기술 글의 결론은 거의 모두 *내가 그 자리에서 이렇게 풀어보니 더 자연스러웠다* 의 묶음이다. 단정 톤을 **경험적 결론 톤** 으로 바꾸면, 같은 주장을 하면서도 읽는 사람이 자기 맥락에 맞게 받아들일 여지가 생긴다.

### 변환 패턴

| 단정 톤 (정답인 척) | 경험적 결론 톤 (해보니 그렇더라) |
|---|---|
| "~해야 한다" | "~하는 편이 나았다" / "~해두면 결이 덜 흐트러졌다" |
| "~하면 안 된다" | "~하지 않는 쪽이 좋았다" / "~할수록 어색해졌다" |
| "~이다 / ~인 것이다" | "~인 것 같았다" / "~로 느껴졌다" |
| "~한 길이다" | "~한 길로 보였다" / "~인 듯했다" |
| "거의 유일한 길이다" | "내 경우엔 가장 덜 흔들렸다" |
| "~할수록 ~된다" (예언) | "~할수록 ~되곤 했다" (관찰) |
| "~다. 그게 옳다" | "~다. 적어도 내 자리에선 그쪽이 나았다" |

### 자주 쓰는 경험적 표현

* **"~해보니"** : 내가 시도해본 결과임을 명시
* **"~인 듯했다"** / "~인 것 같았다" : 단정 대신 인상
* **"~ㄴ 편이 나았다"** : 비교 위에 선 결론
* **"~ㄹ수록 ~하더라"** : 관찰의 누적
* **"내 경우엔"** / "적어도 내 자리에선" : 일반화 범위 한정
* **"~게 풀어보니 결이 덜 흐트러졌다"** : 미적 결과 전달

### 변환 예시

**Before** (단정):
> 이름은 의도를 담아야 한다. 테이블 합성어로 짓는 순간 그 객체는 SQL 의 부산물이 된다. 이걸 한 객체에 섞지 않는 것이 거의 유일한 길이다.

**After** (경험적):
> 이름이 의도를 담아두면, 그 객체가 어디 살아야 하는지도 자연스럽게 따라오는 듯했다. 테이블 합성어로 짓고 나면 그 객체는 SQL 의 부산물처럼 읽혔다. 이 둘을 한 객체에 섞지 않으려고 해보니, 모호해지는 일이 확실히 줄어들었다.

### 단정 톤이 살아도 되는 자리

모든 문장을 경험형으로 바꾸면 글이 흐물흐물해진다. 다음 자리만큼은 단정 톤으로 둔다.

* **마지막 잠언** : 굵게 + 기울임의 한 줄. 여기서 흐물거리면 글이 안 닫힌다.
* **TL;DR 의 핵심 대조 한 줄** : 정의나 대조 (예: *"일치하면 우연이고, 다르면 정상이다"*).
* **개념 정의** : "Aggregate 는 ~다", "Read Model 은 ~다" 같은 용어 정의는 사실 진술.

본문 결론과 챕터 마무리는 경험형으로, 잠언과 정의는 단정형으로. 이 둘이 섞여야 글이 단단하면서도 강요하지 않는다.

## 4. 같은 의미 반복 빼기

AI는 같은 말을 다른 표현으로 두 번 한다.

### 예시

**Before**:
```
VO 는 검증을 위한 것이 아니다. 그것은 값에 이름을 주기 위한 것이다.
검증은 그 이름이 데려오는 부수 효과의 일부일 뿐이다.
```

**After**:
```
VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이다.
```

같은 의미를 두 번 하면 한 번만 한다.

## 5. "~합니다" vs "~다" 통일

요한의 글은 **평어체 ("~다") 가 기본**이다. 정중체와 섞이면 어색하다.

### 변환 예시

| 정중체 | 평어체 |
|---|---|
| "~했습니다" | "~했다" |
| "~합니다" | "~한다" |
| "~이었습니다" | "~이었다" |
| "~할 수 있습니다" | "~할 수 있다" |
| "~지 않을까요" | "~지 않을까" |

다만 **글 전체 톤을 평어체로 통일**하기로 정했다면 일관되게 적용해야 한다.

## 6. 챕터 마무리 다듬기

AI는 챕터를 "그래서 다음 장에서는 ~을 살펴보겠다" 같은 메타 문장으로 끝낸다. 이걸 **자연스러운 의문문**으로 바꾼다.

### 변환 패턴

**Before**:
```
이렇게 VO + Converter 방식의 한계를 살펴봤다.
다음 장에서는 다른 접근법을 알아보겠다.
```

**After**:
```
VO 를 늘릴수록 Converter 도 함께 늘어난다. 또 다른 방법은 없을까?
```

## 7. 도입부 다듬기

AI는 도입부에 **"이 글에서는 ~을 다룰 것이다"** 같은 메타 설명을 넣는다. 이걸 빼고 바로 본론으로 들어간다.

### 빼야 할 도입부 패턴

* "이 글에서는 ~에 대해 알아보자"
* "오늘은 ~에 대해 정리해보려고 한다"
* "최근 ~을 고민하다가 ~을 알게 됐다. 그 과정을 정리한다"
* "같은 질문을 세 번째 받고 있다..." (감성 도입부)

### 좋은 도입

TL;DR 다음에 바로 1장 코드부터 시작하거나, 한 줄짜리 화두만 던지고 들어간다.

## 8. 마지막 잠언 다듬기

마지막 잠언은 **짧고 단정적**이어야 한다. 본문이 경험적 톤이어도 이 한 줄은 단정형으로 둬야 글이 닫힌다.

### Before (늘어지는)

```
세 번의 답을 거치면서 정리된 것은 이렇다... (본문)

VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이었다. 
검증은 그 이름이 데려오는 부수 효과의 일부일 뿐이었다.

다음 프로젝트에서 또 같은 질문 앞에 서면, 답이 또 달라질지도 모른다. 
그땐 그때의 거슬림을 또 정리하면 된다.
```

### After (짧고 단정적)

```
세 번의 답을 거치면서 정리된 것은 이렇다... (본문)

***VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이다.***
```

* "~이었다" 과거형 → "~이다" 현재형
* 늘어지는 후일담 빼기
* 굵게 + 기울임으로 시각적 마무리

## 9. 강조 장치 정리

### 줄여야 할 강조

* 따옴표 강조 ("정말로", "사실은") — AI 티
* 말줄임표 (...) — 거의 안 씀
* 굵은 글씨 남발 — 한 문단에 한두 개만
* 이모지 / 느낌표 — 사용 안 함

### 적절한 강조

* **굵은 글씨** : 핵심 개념 한 단어 또는 짧은 구절
* `코드 인라인` : 변수명, 클래스명, 키워드
* > 인용구 : 핵심 원칙, 잠언

## 10. 다듬기 체크리스트

초안을 다 쓴 뒤 다음을 확인한다.

### 문장 차원

- [ ] "~다. ~다. ~다." 짧은 문장이 3개 이상 연속되지 않는가?
- [ ] "~지만", "~기 때문에", "~인데" 같은 연결어미를 쓰고 있는가?
- [ ] 같은 의미를 두 번 반복한 부분이 없는가?

### 단어 차원

- [ ] "거슬렸다", "어색해졌다" 같은 감정 표현이 과다하지 않은가?
- [ ] "~라는 사실이다", "~라는 의미다" 같은 명사화가 과다하지 않은가?
- [ ] "흥미롭게도", "안타깝게도" 같은 부사가 들어 있지 않은가?

### 톤 차원

- [ ] 결론·챕터 마무리가 "이게 정답이다" 식 단정 톤이 아니라 "해보니 더 나았다" 식 경험적 톤으로 끝나는가?
- [ ] "~해야 한다", "~할 수밖에 없다", "~인 것이다" 같은 강제·단정 어미가 본문에 과다하지 않은가?
- [ ] 잠언·개념 정의 자리에는 단정 톤이 살아있는가? (모두 흐물거리면 글이 안 닫힌다)

### 구조 차원

- [ ] 도입부에 "이 글에서는 ~" 같은 메타 설명이 있지 않은가?
- [ ] 챕터 마무리가 자연스러운 의문문 또는 결론으로 끝나는가?
- [ ] 마지막 잠언이 짧고 단정적인가?
- [ ] 정중체와 평어체가 섞이지 않았는가?

### 분량 차원

- [ ] 한 문단이 너무 길지 않은가? (4문장 넘으면 의심)
- [ ] 추상적 원칙만 있고 구체적 코드/사례가 없는 챕터가 있지 않은가?
- [ ] 굵은 글씨가 한 문단에 너무 많이 들어가지 않았는가?

## 11. 변환 작업 우선순위

다듬을 때 시간 없으면 이 순서로:

1. **짧은 문장 연결** (가장 큰 효과) — §1
2. **AI 감정 표현 제거** — §2
3. **단정 톤 → 경험적 결론 톤** — §3
4. **"~합니다" / "~다" 통일** — §5
5. **마지막 잠언 다듬기** — §8
6. **챕터 마무리 자연스럽게** — §6

이 여섯 가지만 챙겨도 80% 의 AI 티는 사라진다.

## 12. 변환 예시 모음

실제 변환 사례를 모아둔다. 비슷한 패턴을 만나면 참고한다.

### 사례 A: 끊어진 문장 → 이어진 문장

**Before**:
> VO 는 답이었다. 정확히는, 답인 줄 알았다. 이메일 검증을 한 곳에 모았다. 어디서 이메일을 만들든 같은 규칙을 통과한다. 컴파일러도 헷갈리지 않는다. 타입 자체가 검증된 사실을 보장한다.

**After**:
> VO 를 도입하면 어떻게 될까? 이메일 검증을 한 곳에 모았기 때문에 어디서 이메일을 만들든 같은 규칙을 통과하고, 컴파일러도 헷갈리지 않으니 타입 자체가 검증된 사실을 보장한다.

### 사례 B: AI 감정 표현 제거

**Before**:
> 여기까지는 좋았다. 그런데 코드를 더 짜다 보니 거슬리는 자리들이 줄줄이 나왔다.

**After**:
> 여기까지는 좋았는데, 코드를 더 짜다 보니 몇 가지 문제가 보이기 시작했다.

### 사례 C: 명사화 풀어주기

**Before**:
> VO 가 가진 "항상 유효함" 보장이 nullable 자리에 들어가는 순간 비대칭이 생긴다는 것이다.

**After**:
> 원시 타입이었다면 한 줄로 끝날 일이 세 줄이 되어버리는 셈이다.

(같은 의미인데 더 구체적이고 짧게)

### 사례 D: 도입부 빼기

**Before**:
```
같은 질문을 세 번째 받고 있다. 새 프로젝트에서 회원 도메인을 다시 짜면서, 
이메일과 전화번호와 비밀번호를 손에 쥐고 또 멈춰 섰다.

답은 매번 달랐다. 그리고 매번 어딘가가 거슬렸다. 
이번엔 그 거슬림의 정체를 정리해두려 한다.

---

## 1. String 원시타입
```

**After**:

### 사례 F: 단정 톤 → 경험적 결론 톤

**Before** (정답을 내리는 톤):
> 조회 결과 객체에 비즈니스 로직을 넣고 싶어진다면 그건 도메인 객체로 자라고 싶다는 신호이니 Aggregate 로 모델링하고, 그렇지 않다면 Read Model 로 두고 도메인 패키지 밖에 둔다. 이 둘을 한 객체에 섞지 않는 것이 객체가 모호해지지 않는 거의 유일한 길이다.

**After** (해보니 이쪽이 나았다 톤):
> 조회 결과 객체에 비즈니스 로직을 넣고 싶어지면, 그건 도메인 객체로 자라고 싶다는 신호처럼 느껴졌고, 그럴 땐 Aggregate 로 모델링하는 편이 나았다. 그렇지 않은 객체는 Read Model 로 두고 도메인 패키지 밖에 두는 쪽이 결을 덜 흐트러뜨렸다. 이 둘을 한 객체에 섞지 않으려고 해보니, 적어도 내 자리에선 모호해지는 일이 확실히 줄어들었다.

  직접 코드를 수정하거나 plan 본문을 새로 작성하지 않는다. 본 스킬은 *결정의 박제* 만 담당한다.

# record-decision

## 0. 호출 시점

다음 조건 중 하나가 충족되면 호출:

- 사용자가 명시적으로 요청 — "결정 기록해줘" / "decision.md 에 추가해줘" / "이 선택 박제해줘" / "이거 남겨줘"
- 주차 plan 작성 / 검토 중 *대안 비교 + 선택 + 근거* 가 한 번에 정리된 시점
- plan 본문이 *공간 상 길어지는 것을 피하면서* 트레이드오프 기록을 남기고 싶은 시점
- 사용자가 "왜 X 를 선택했지?" 같은 질문을 던졌고, 답변이 *미래에도 재사용될 기준* 인 경우

다음 경우는 호출 X:

- 일회성 버그 수정 사유 (그건 `verify-code` 회귀 룰 영역)
- 코드 변경 자체 (그건 commit 메시지 / plan 본문 영역)
- 사람의 책임 / 일정 추적 (그건 별도 프로젝트 관리 도구 영역)
- 자동 게이트 — 본 스킬은 *명시 호출 전용*

## 1. 산출물 위치

```
docs/plan/week{n}/decision.md     ← 본 스킬이 누적 갱신하는 파일
docs/plan/week{n}.md              ← plan 본문 (별도 스킬 / 사용자 작성)
```

`docs/plan/week{n}/` 디렉토리가 없으면 생성한다 (Write 툴이 부모 디렉토리를 자동 생성).

## 2. 입력 형식

사용자가 다음 정보를 제공 (또는 대화 중 조립):

| 항목 | 필수 | 설명 |
|---|---|---|
| 주차 번호 | ✅ | 예: `4`. plan 본문이 어느 주차인지 |
| 결정 주제 | ✅ | 예: "더블부킹 락 선택", "Coupon Aggregate 분리" |
| 대안 | ✅ | 최소 2개. 각 대안의 *특징* 도 같이 |
| 선택 | ✅ | 어느 대안을 골랐는지 + 한 줄 근거 |
| 근거 | ✅ | 비즈니스 + 기술 양쪽 |
| 트레이드오프 | ✅ | *감수하는 비용* — 없는 결정은 의심해야 함 |
| 미래 재검토 | ⭕ | 언제 / 어떤 조건에서 본 결정을 다시 봐야 하는지 |
| 참조 | ⭕ | plan 본문 위치 / design doc 위치 / 외부 자료 |

## 3. 출력 템플릿

다음 형식으로 `docs/plan/week{n}/decision.md` 에 **누적 추가**:

```markdown
## D-{번호}. {결정 주제}

**상황.** {배경 / 시나리오 — 왜 이 결정이 필요했는가}

**대안.**
- (A) **{대안 1}** — {특징}
- (B) **{대안 2}** — {특징}
- (C) **{대안 3}** — {특징, 있으면}

**선택.** ({선택지}) — {한 줄 근거}

**근거.**
- *비즈니스* : {왜 이게 도메인적으로 옳은가 — 사용자 경험 / 도메인 의미 / 정책 정합}
- *기술* : {성능 / 정합성 / 운영 / 회복 비용}
- *대안의 한계* : {다른 대안이 왜 부적합한가}

**감수하는 비용.** {트레이드오프}

**미래 재검토.** {언제 / 어떤 조건에서 본 결정을 다시 봐야 하는지}

**참조.** {plan 본문 위치, design doc, 외부 자료}

---
```

## 4. 절차

1. **`docs/plan/week{n}/decision.md` 의 존재 여부 확인.**
   - 없으면 frontmatter 와 함께 신설:
     ```markdown
     # {n}주차 의사결정 기록 (Decision Log)

     > 본 문서는 `docs/plan/week{n}.md` 진행 중 내려진 *주요 결정의 기준 + 대안 비교 + 트레이드오프* 를 박제한다.
     > 분담:
     > - `docs/plan/week{n}.md` = *무엇을 할 것인가*
     > - `docs/plan/week{n}/decision.md` (본 문서) = *왜 그렇게 결정했는가*
     ```
   - 있으면 기존 내용 그대로 보존, 아래에 누적 추가.

2. **마지막 D-N 의 다음 번호로 추가.**
   - 기존 결정의 *번복* 인 경우 — 원본 결정을 지우지 않고 새 D-N 으로 추가하면서 본문에 `**대체:** D-{이전번호}` 명시.

3. **plan 본문 (`docs/plan/week{n}.md`) 의 해당 섹션에 역참조 추가.**
   - 형식: `(상세 근거: docs/plan/week{n}/decision.md D-{번호})`
   - plan 본문이 이미 *결정의 결과* 를 박제하고 있어야 함. 본 스킬은 *결정의 기준* 만 추가.

4. **누적 정책 섹션 유지.**
   - 본 문서의 마지막에 *누적 정책* 섹션이 있는지 확인. 없으면 추가:
     ```markdown
     ## 누적 정책

     - 새 결정이 발생하면 본 문서에 D-N 으로 누적 추가.
     - 기존 결정이 *번복* 되면 *원본을 지우지 않고* 새 D-N 으로 추가하면서 "**대체:** D-{이전번호}" 명시.
     - 본 plan 종료 후 본 문서는 read-only — *그 시점의 판단* 의 박제이므로 회수하지 않는다.
     ```

## 5. 결정에 *반드시* 포함되어야 할 것

- *왜 다른 대안이 부적합한지* (제거된 대안의 비용 / 위험)
- *언제 재검토가 필요한지* (예: "분산 환경 합류 시점", "선착순 발급 합류 시점")
- *비즈니스 관점의 근거* — 단순 기술 비교가 아니라 *사용자 경험 / 도메인 의미* 까지
- *트레이드오프* — 없는 결정은 의심해야 함

## 6. 결정에 *포함되지 말아야* 할 것

- 코드 변경 자체 — commit 메시지 / plan 본문 영역
- 일회성 버그 수정 사유 — verify-code 회귀 룰 영역
- 사람의 책임 / 일정 — 별도 프로젝트 관리 도구 영역
- *결과만 있고 근거가 없는 결정* — "X 채택" 만 적으면 미래의 재사용 가치 0

## 7. 호출 예시

### 예시 1 — 새 결정 박제

```
사용자: "Inventory 락은 비관적 락으로 가기로 했어. 5→2→1 의 반복 재시도 UX 가 최악이라서. 이거 박제해줘."
→ Skill(record-decision)
   - 주차 = 4
   - 주제 = "Inventory 더블부킹 차단 — 비관적 락 vs Atomic UPDATE"
   - 대안 = 비관적 락 / Atomic UPDATE / 낙관적 락
   - 선택 = 비관적 락
   - 근거 = 공유 자원 + 순서 중요 + UX 명확성
   ...
```

### 예시 2 — 기존 결정 번복

```
사용자: "5주차 가서 Inventory 락 정책 다시 봤더니 Hold + TTL 로 가기로 했어. 비관적 락은 짧은 차감 구간만 잡고. 박제해줘."
→ Skill(record-decision)
   - 주차 = 5
   - 주제 = "Inventory 동시성 — Hold + TTL 로 진화"
   - 본문에 "**대체:** week4/decision.md D-1 ① (비관적 락 단독)" 명시
```

## 8. 산출물 검증 (호출 후 자가 점검)

- [ ] `docs/plan/week{n}/decision.md` 가 존재
- [ ] 신규 결정이 D-N 형식으로 누적 추가됨 (기존 결정 보존)
- [ ] 본 결정에 *비즈니스 근거 + 기술 근거 + 트레이드오프* 가 모두 있음
- [ ] *미래 재검토 조건* 이 명시됨 (없으면 *영구 결정* 으로 간주, 그게 맞는지 사용자 확인)
- [ ] plan 본문 (`docs/plan/week{n}.md`) 에 역참조 추가됨

## 9. 본 스킬이 *하지 않는 것*

- ❌ plan 본문 (`docs/plan/week{n}.md`) 을 새로 작성 — 그건 별도 작업 (사용자 / 다른 스킬)
- ❌ 코드 변경 — 본 스킬은 *문서 박제* 만
- ❌ 자동 게이트로 호출 — 명시 호출 전용
- ❌ 결정의 *옳고 그름* 판단 — 본 스킬은 *기록만* 담당, 결정 자체는 사용자 / 시니어가 내림

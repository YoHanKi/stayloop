# 블로그 작성 스킬

> 요한의 기술 블로그 (velog.io/@dygks684) 작성 패턴을 정리한 가이드. 새 글의 구조를 잡고 톤을 결정할 때 참고한다.

---

## 1. 글의 핵심 구조

요한의 글은 **"가설 → 흔들림 → 재정의"** 패턴을 따른다.

```
1. 자명해 보이는 전제로 시작
   ("우리는 보통 ~하게 처리한다")
2. 그 전제가 흔들리는 순간을 보여줌
   (실험, 실측, 사례, 거슬렸던 경험)
3. 전제 자체를 다시 정의하며 마무리
   ("바뀐 건 숫자가 아니라 전제였다")
```

이 구조가 글의 척추다. 정보 전달이 목적이라도, 결국 **"내가 무엇을 다시 봤는가"** 가 글의 중심이어야 한다.

---

## 2. 제목 패턴

요한의 제목은 **도발적 질문 또는 통념 뒤집기** 형식이다.

### 자주 쓰는 패턴

* **"~ 정말 ~할까"** : "리밸런싱은 정말 잠깐 멈출 뿐일까", "대기열은 정말 공정할까"
* **"그럼에도 ~ 한다"** : "그럼에도 랭킹은 멈추지 않는다"
* **"~이 ~이 아닐 수 있다"** : "오늘의 설정은 내년의 설정이 아닐 수 있다"
* **"~ 어떻게 해야 할까"** : "엔티티의 VO, 어떻게 해야 할까"
* **"~하면 ~까"** : "캐시하면 끝일까"

### 피해야 할 패턴

* "Kotlin + JPA의 함정 8가지" 같은 정보형 제목 → 너무 AI/리스티클 톤
* "~하는 방법" → 너무 평범
* 느낌표·이모지 → 사용 안 함

---

## 3. TL;DR 패턴

글 맨 위에 짧은 요약을 둔다.

### 형식

```markdown
> **TL;DR**
- **항목 A** : 한 줄 결론. 핵심 포인트.
- **항목 B** : 한 줄 결론. 핵심 포인트.
- **항목 C** : 한 줄 결론. 핵심 포인트.
```

### 원칙

* 불릿 3~6개. 시간/인과 순으로 흐름이 잡히도록
* 한 불릿당 한 문장 또는 두 문장
* 단점만 나열하지 말고 **장단점 균형 있게** 적기
* 마지막 불릿이나 별도 줄에 **한 줄 잠언** 으로 마무리 가능

---

## 4. 본문 구조

### 챕터 제목

* **방식의 이름이 곧 챕터 제목** : "1. String 원시타입", "2. VO + AttributeConverter", "3. VO + @Embeddable"
* 글 전체의 흐름이 챕터 제목만 봐도 보이도록

### 챕터 마무리 패턴

각 챕터를 **다음 챕터로 넘어가는 의문문** 으로 마무리한다.

```markdown
... VO 를 늘릴수록 Converter 도 함께 늘어난다. 또 다른 방법은 없을까?
```

```markdown
... 좀 더 좋은 방법이 없을까? VO 가 해답이 될 수 있을까? 바로 시작해보자.
```

이게 글의 흐름을 끊기지 않게 만든다.

### 코드 + 설명 + 결과

```markdown
설명 한 문단

```kotlin
실제 코드
```

코드가 보여주는 것의 의미
```

코드 → 설명 → 코드 → 설명 리듬으로 가야지, 코드만 줄줄이 붙이면 안 된다.

### 표 사용

대안 비교, before/after, 가설/실측 같은 자리에 자주 사용.

```markdown
| 항목 | 이전 | 이후 |
|---|---|---|
| 매핑 | Converter | @Embeddable |
| 파일 수 | N+N | N |
```

## 5. 글의 마무리

마지막 잠언은 **평어체로 짧고 단정적**이다.

```markdown
***VO 는 검증을 위한 것이 아니라, 값에 이름을 주기 위한 것이다.***
```

* 굵게 + 기울임으로 강조
* 본문이 정중체여도 잠언만은 평어체
* 늘어지는 마무리 ("다음 프로젝트에서도 이런 고민이 계속될 것 같다") 는 피한다

다른 글의 잠언 예시:
* "기술은 근거 위에 올려야 한다"
* "오늘의 설정은 내년의 설정이 아닐 수 있다"

---

## 6. 톤과 어휘

### 기본 톤

* **평어체 ("~다")** 가 기본
* 정중체와 평어체를 섞지 말 것
* 감정 표현보다는 담담한 서술

### 자주 쓰는 표현

* "~지 않을까?" / "~할까?" — 화두 던지기
* "~한 셈이다" — 결론 풀어내기
* "~기 때문이다" — 인과 명료화
* "바로 시작해보자" — 챕터 도입

### 피하는 표현

* "거슬렸다" / "어색해졌다" — AI 감정 표현
* "정확히는, ~인 줄 알았다" — 극적 장치
* "~라는 사실이다" — 명사화 과다
* "~을 깨달았다" — 과한 회고감

---

## 7. 문단 길이

* 한 문단은 보통 **2~4문장**
* 너무 길면 코드 블록이나 표로 끊어주기
* 한 문장이 끝없이 이어지면 잘라야 하지만, 짧은 문장 두 개를 인위적으로 만들지는 말 것

## 8. 글의 구체성

요한의 글이 좋은 이유는 **추상적 원칙이 아니라 구체적 코드와 거슬림** 이 살아있기 때문이다.

### 좋은 예

```markdown
### 2-2. 마이그레이션 데이터 앞에서 부팅이 멈춘다

운영 데이터엔 옛날 형식이 살아있을 수 있는데, 가령 `010-1234-5678` 으로 
통일하기 전의 `01012345678` 같은 값들이다.

서비스가 부팅하면서 회원 100건쯤 hydrate 되다가 예외가 터지는데, 
운영 데이터가 잘못된 게 아니라 과거의 규칙을 따르고 있었을 뿐이다.
```

→ 구체적 형식, 구체적 시점, 구체적 결과

### 나쁜 예

```markdown
### 2-2. 데이터 호환성 문제

VO 의 검증이 강하면 기존 데이터와 호환되지 않을 수 있습니다.
이런 경우 부팅에 문제가 생길 수 있으므로 주의가 필요합니다.
```

→ 추상적, 일반론, 자기 경험 없음

새 글을 시작하기 전 다음을 확인한다.

- [ ] 제목이 **도발적 질문 또는 통념 뒤집기** 형식인가?
- [ ] 챕터 구조가 **시간/인과 순** 으로 흐르는가?
- [ ] 각 챕터에 **구체적 코드 또는 사례** 가 있는가?
- [ ] 각 챕터 끝에 **다음 챕터로 넘어가는 연결고리** 가 있는가?
- [ ] 마지막 잠언이 한 줄로 정리되는가?
- [ ] TL;DR이 글 전체 흐름을 보여주는가?

## 10. 글의 분량 감각

* 짧은 글 (5분 읽기) : 한 가지 주제를 깊게 — VO 같은 단일 개념
* 중간 글 (7~10분) : 두세 가지 방식 비교 — 이번 VO 글
* 긴 글 (12~20분) : 종합 회고 — 한 프로젝트 전체

분량보다 중요한 건 **불필요한 문단을 빼는 것**. 같은 이야기를 두 번 하지 않고, 본문을 다 읽기 전에 결론이 드러나지 않도록 한다.

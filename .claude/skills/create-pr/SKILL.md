PR 은 **변경된 코드의 외부 표현**이다. 이 스킬은 누락 없이 일관된 형식의 PR 을 만들도록 보조하며, 코드를 직접 작성하지 않는다.

---

### 0️⃣ 사전 게이트 확인

다음이 모두 통과되어 있지 않으면 PR 생성에 들어가지 않는다.

- `verify-architecture`: ✅ PASS
- `verify-tests`: ✅ PASS
- `git status`: 작업 트리 클린 (`pr.md` 작성 단계에서만 새 파일 추가 허용)

하나라도 미충족이면 사용자에게 사유를 묻고, 해당 게이트를 먼저 호출하도록 안내한다.

---

### 1️⃣ 브랜치 컨벤션

브랜치 이름은 변경의 성격을 prefix 로 드러낸다.

| Prefix | 용도 | 예시 |
|---|---|---|
| `feature/` | 신규 기능 | `feature/reservation` |
| `fix/` | 버그 수정 | `fix/password-policy` |
| `refactor/` | 동작 보존 리팩토링 | `refactor/user-vo` |
| `migration/` | 구조/스키마 마이그레이션 | `migration/user` |
| `document/` | 문서 단독 PR | `document/user-architecture` |
| `chore/` | 인프라·빌드·메타 | `chore/gradle-bump` |
| `skills/` | 프로젝트 전용 스킬 | `skills/verify-architecture` |

확인 항목:

- 현재 브랜치가 `main` 이면 즉시 새 브랜치로 분기 (main 직접 푸시 금지)
- 현재 브랜치가 위 prefix 중 하나에 해당하지 않으면 사용자에게 변경 의도를 물어 prefix 결정
- base 브랜치는 기본 `main`. 다른 long-lived 브랜치를 base 로 삼는 경우 사용자에게 명시 확인

---

### 2️⃣ 커밋 메시지 컨벤션

기존 git log 의 패턴을 따른다.

```
<prefix> : <한 줄 요약 (한국어, 마침표).>
```

| Prefix | 의미 |
|---|---|
| `feat` | 신규 기능 (외부 동작 변화) |
| `fix` | 버그 수정 |
| `refactor` | 동작 보존 변경 |
| `migration` | 구조 마이그레이션 (코드 이동/이름 변경 포함) |
| `docs` | 문서만 변경 |
| `chore` | 빌드·툴·메타 |
| `skills` | `.claude/skills/` 아래 변경 |

예: `migration : 유저 아키텍처 마이그레이션.`, `docs : 유저 아키텍처 마이그레이션 PR 문서 추가.`

여러 논리적 변경이 한 PR 에 섞여 있다면 커밋을 분리하도록 권장한다 (강제하지 않음).

---

### 3️⃣ pr.md 작성

위치: `documents/feature/{topic}/pr.md`. `{topic}` 은 브랜치명의 후행 부분과 일치시킨다 (예: `document/user-architecture` → `documents/feature/user-architecture/pr.md`).

**파일 첫 줄은 PR title 한 줄.** GitHub PR 생성 시 그대로 제목으로 사용한다 (`gh pr create --title "$(head -n1 pr.md | sed 's/^# //')"`). 형식:

```
# <prefix>: <한 줄 요약 (한국어, 마침표 없이, 70자 이내)>
```

`<prefix>` 는 커밋 메시지 prefix 와 동일한 어휘(`feat` / `fix` / `refactor` / `migration` / `docs` / `chore` / `skills`). 변경의 *대표* 성격을 따른다.

예:
- `# migration: 유저 도메인 아키텍처 마이그레이션`
- `# skills: PR 생성 스킬(create-pr) 추가`
- `# feat: 예약 도메인 회원-숙소 매칭 추가`

본문 섹션 제목과 순서는 **`.github/pull_request_template.md` 와 1:1로 일치시킨다** (사람이 쓰든 AI 가 쓰든 같은 뼈대여야 협업이 깨지지 않는다). 템플릿이 갱신되면 이 목록도 함께 갱신한다.

1. **배경** — 이 변경이 왜 필요한지를 **PR 본문만 읽고도 이해되도록 1~3줄로 풀어서** 쓴다. "`week3-a.md` 를 참고했다", "결정 블록 16개에 기록했다" 같은 **내부 문서·산출물 지칭이나 메타 참조는 넣지 않는다** — 리뷰어는 그 문서를 열지 않으므로 필요한 맥락은 본문에 직접 풀어 쓴다. 배경이 짧으면 TL;DR 과 합쳐도 된다.
2. **TL;DR** — 본문 요약이 아니라 *본질만 날카롭게* 2~4줄. 리뷰어가 "어디에 시간을 쓸지" 만 잡히면 된다. "A 를 B 로 하여 C 했다" 식 균일한 AI 문장 구조, "~를 답습했다" 같은 군더더기 수식은 피하고 사실을 짧게 끊어 쓴다. 본문(핵심 변경·결정)과 같은 문장을 반복하지 않는다.
3. **구조 변경** — (Optional) 컴포넌트/계층 관계·호출 흐름이 바뀌고 그게 글보다 그림으로 빠를 때만 Mermaid. 파일 1~2개 변경이면 삭제.
4. **핵심 변경** — 어디를 어떻게 바꿨는지 파일/타입 단위 1줄. `path/Type.kt — 요약(전 → 후)`. **AI 가 diff 를 분석해 생성하는 영역**(사람이 손으로 나열하지 않는다). **파일이 많으면(대략 10개 초과) 개별 나열 대신 도메인/계층 단위로 묶어** 그룹 제목 + 묶음당 2~3줄로 정리한다(112개 파일을 그대로 나열하면 가독성이 죽는다).
5. **결정과 대안** — 의사결정 1개당 subsection: (1) 문제·갈림길 산문 → (2) 검토 대안의 장단 → (3) 선택과 결정적 사유. **표를 쓰지 않는다**(결정의 무게가 평탄화된다). 핵심 3~5개. **선택이 자명한 결정(예: `BigDecimal` vs `Double`)은 적지 않는다** — 기술적 갈림길이 실재했거나 비즈니스 규칙상 중대한 선택이었을 때만. 소형 PR 에서 적을 게 없으면 섹션째 삭제.
6. **트레이드오프** — 한 결정에 묶이지 않는 *전역적* 비용만 모은다(예: 파일 수 증가, stereotype 누출). 특정 결정에 종속된 비용은 그 결정의 subsection 안에서 다뤄 중복을 막는다. 없으면 삭제.
7. **위험 요인** — *머지/배포되는 순간* 터질 수 있는 것만. `DB 스키마/데이터 변경` / `파괴적 변경(API·계약)` / `동시성·데이터 정합성` 세 축을 점검해 해당 항목만 적되, 셋 다 해당 없으면 "해당 없음" 한 줄로라도 남긴다. 위험이 있으면 신호만 적지 말고 *대응*(배포 순서·롤백·플래그·버전 병행)을 같이 적는다. "나중에 갚을 부채"는 여기가 아니라 `후속` 으로 보낸다. **동시성 미보장처럼 의도적으로 남긴 한계가 위험이자 부채일 때는 한 곳에만 본문을 쓰고 다른 곳은 한 줄 cross-ref** (예: 위험 요인엔 "현재 더블부킹 가능 → 대응은 후속 참조", 후속엔 닫을 계획). 같은 문단을 두 번 쓰지 않는다.
8. **리뷰 포인트** — 리뷰어가 먼저 봐야 할 파일/규칙 1~3개. 의심스러운 코드·관용 이탈 우선. **대형 PR(파일 수십 개 이상)은 "무엇을 무시해도 되는지" + 추천 리뷰 경로**(예: 도메인 모델 → 도메인 서비스 → Facade → Controller 순)를 함께 적어 리뷰어가 길을 잃지 않게 한다.
9. **검증** — `verify-architecture` / `verify-tests` PASS/FAIL, `./gradlew ktlintCheck && test` 결과, 추가/수정 테스트(단위·통합·E2E), 그리고 필요 시 **증거**(실패·경계 시나리오 로그 / API 응답 JSON / 측정 수치). 게이트 통과는 전제이고 핵심은 "무엇을 어떻게 확인했나". **증거의 로그·수치는 실제 실행 결과만 적는다 — 돌려보지 않은 값을 추정해 채우지 않는다.** 확인하지 못한 칸은 비워 두고 작성자에게 채우라고 표시(`<!-- 작성자 확인 필요 -->`)한다.
10. **후속** — 이번 PR 에서 **의도적으로 제외한 기능·구현**이 무엇인지만 적는다. "몇 주차에 한다", "다음 스프린트" 같은 **일정·순번은 리뷰어에게 의미가 없으므로 넣지 않는다.** 무엇을 왜 이번 범위에서 뺐는지(아직 무엇이 없는지)만 남긴다. 없으면 삭제.

> **AI 가 초안 잡는 영역 vs 사람이 채우는 영역.** `핵심 변경`(diff 요약)·`위험 요인` 초안은 AI 가 잡는다. `결정과 대안`의 사유, `검증`의 실행 증거(로그·수치), 배포 전략은 작성자의 판단·실측이 필요하므로 AI 는 빈칸 + `<!-- 작성자 확인 필요 -->` 로 남기고 지어내지 않는다.

> 표(Table)는 **결정·구조·이전vs이후 비교**에 쓰지 않는다 — 산문이나 mermaid 가 결정의 무게를 더 잘 전한다. 표는 `위험 요인` 체크나 다축 데이터처럼 정말 격자가 맞을 때만.

작성 원칙:

- **WHAT 보다 WHY**. diff 가 알려주는 것은 다시 적지 않는다. (`핵심 변경` 만 예외 — diff 요약이 목적)
- 대안을 비교한 흔적을 남긴다 — "이 코드는 (A) 가 아닌 이유" 가 PR 본문에 있다.
- 보안/성능/동시성처럼 리뷰어가 놓치기 쉬운 함정은 `위험 요인` 에 모은다.
- 문체는 **공손한 말투(합니다/습니다체)** 로 통일한다. 한 문서 안에서 평문체와 섞지 않는다.
- **일반 원리를 가르치지 않는다.** 리뷰어는 시니어다. "도메인 서비스가 트랜잭션을 알면 단위 테스트에 DB 가 필요하다" 같은 교과서 설명은 빼고, *이 변경에서 왜 그 패턴을 택했는지*만 한두 줄로 남긴다. 결정의 사유는 "원리 강의" 가 아니라 "이 코드베이스의 갈림길" 이어야 한다.
- **표준 패턴 답습이면 다이어그램을 그리지 않는다.** `구조 변경` mermaid 는 팀의 표준 레이어드 흐름을 그대로 따른 경우 생략한다. 비동기 이벤트·외부 연동·평소와 다른 트랜잭션/인가 경계처럼 *코드만 봐선 안 잡히는 흐름*이 있을 때만 그린다.
- **제품/비즈니스 언어로 쓴다.** "N주차 과제", "학습 진도" 같은 부트캠프 메타 표현은 본문에 쓰지 않는다. 요구사항·설계 문서는 *범위의 출처* 로 링크만 걸고, 변경 자체는 "어떤 제품 능력을 추가했는가" 로 서술한다. (단 `verify-architecture` 같은 실제 레포 게이트·툴 이름은 메타가 아니라 실재 도구이므로 그대로 쓴다.)
- **건조하게.** "명시적 비용으로 받아들였다" 같은 비장한 자기변호 대신 "레이어 분리를 위해 수용" 처럼 사실만. 감정·방어적 수사는 뺀다.
- **강의·블로그 어휘를 피한다.** "함정" 대신 "주의/유의", "~를 박아 두고" 같은 구어체 직역투 대신 "기록하고/명시하고". 시니어 간 PR 의 정제된 기술 레지스터를 유지한다.

**마지막 단계 — AI 티 제거 다듬기 (초안 완료 후 반드시 1회).** pr.md 초안을 다 쓴 뒤 사람의 눈으로 한 번 더 읽으며 기계가 쓴 흔적을 덜어낸다.

- 모든 bullet 이 같은 길이·같은 구조(`A 는 B 다`)로 줄 맞춰 늘어선 균일함을 깬다 — 문장 길이를 들쭉날쭉하게 둔다.
- "~를 통해 / ~함으로써 / 이는 ~을 의미한다 / 결론적으로" 같은 영어 직역투·연결어 남발을 친다.
- 한 문장에 수식어가 3개 이상 붙은 곳, 같은 말을 다르게 두 번 한 곳을 덜어낸다.
- 당연한 사실을 굳이 설명한 문장(시니어가 이미 아는 것)을 지운다.
- 다듬은 뒤 "사람이 5분 안에 읽고 리뷰를 시작할 수 있는가" 로 자가 점검한다. 분량보다 밀도다.
- **큰 PR 은 리뷰 부담을 줄이는 길을 제공한다.** 분할이 어려우면(한 브랜치로 묶기로 한 경우 등) 논리적 커밋 순서를 리뷰 경로로 안내하고, 패턴 반복 영역은 "한 도메인만 보면 나머지는 동형" 임을 *근거와 함께* 짚는다.

### 4️⃣ Push & PR URL 산출

```
git push -u origin <branch>
```

- 인증 실패: Windows 측 자격증명 매니저가 필요할 수 있으므로 PowerShell 환경에서 재시도.
- 푸시 성공 후, GitHub Compare URL 을 생성해 사용자에게 전달:

```
https://github.com/{owner}/{repo}/compare/{base}...{head}?expand=1
```

`gh` CLI 가 있으면:

```
gh pr create --base {base} --head {head} --title "<커밋 메시지 1줄>" --body-file documents/feature/{topic}/pr.md
```

`gh` 가 없으면 Compare URL 만 제공하고 사용자가 브라우저에서 제출하도록 안내. **본문은 pr.md 의 내용을 그대로 사용**하도록 한다 (이중 작성 금지).

### 5️⃣ 출력 포맷

```markdown
## create-pr 결과: {기능명}

### 사전 게이트
- verify-architecture: ✅ / ❌
- verify-tests:        ✅ / ❌

### 브랜치
- base: main
- head: {prefix}/{topic}
- 신규 푸시: ✅ / 기존 동기화

### 커밋
- {short-sha} {prefix} : {요약}

### 문서
- documents/feature/{topic}/pr.md ({lines}줄)

### PR
- Compare URL: https://github.com/{owner}/{repo}/compare/main...{head}?expand=1
- (gh 사용 시) PR URL: ...

### 다음 액션
- 사용자가 Compare URL 에서 제목 확인 후 "Create pull request" 클릭
- 리뷰어 지정 / 라벨 / 마일스톤 부착
```

### 6️⃣ 톤 & 원칙

- **PR 본문(pr.md)을 새로 짜주지 않는다.** 골격을 안내하고 비어 있는 항목을 지적한다.
- **푸시·PR 생성은 반드시 사용자에게 1회 확인 후 진행** (외부에 노출되는 작업).
- main 직접 푸시·force push 는 절대 시도하지 않는다.
- 한국어 응답 기본.

# experiment-recurse

## 0. 호출 시점

다음 조건 중 하나가 충족되면 호출:

- 사용자가 명시적으로 요청 — "실험 검토해줘" / "허점 있는지 봐줘" / "Skill(experiment-recurse)"
- 실험 박제 (예: `documents/feature/{topic}/experiments-results.md` 또는 `docs/plan/week{n}/decision.md`) 가
  *처음 작성된 직후* — 박제만으로 결정을 굳히기 전 *최소 1회 재귀 검토*
- 실험 결과의 *가설과 측정값이 어긋남* / *코드 라벨링 버그가 박제에 노출됨* 이 발견된 시점
- 본 라운드의 결정이 *후속 라운드* (5주차+) 에서 재사용될 예정인 경우 — 재현 가능성 강화 가치 큼

다음 경우는 호출 X:

- 일회성 typo / 환경 변수 수정 같은 *측정 결과 무관 변경*
- 측정 결과가 *비즈니스 결정* (쿠폰 복원 정책 / 다국적 통화 등) 에 종속된 경우 — 측정으로 결정 못 함
- *영구 회귀 가드 테스트* — 그건 `verify-tests` 영역
- 자동 게이트로 호출 X — 본 스킬은 *명시 호출 전용*

## 1. 입력

| 항목 | 필수 | 설명 |
|---|---|---|
| 박제 위치 | ✅ | 예: `documents/feature/concurrency-control/experiments-results.md` |
| 실험 코드 위치 | ⭕ | 코드 삭제 전이면 본 위치도 검토. 삭제 후라면 박제만으로 |
| 재귀 한도 | ⭕ | 기본 *최소 1, 최대 3*. 사용자가 명시하면 그대로 |

## 2. 허점 카테고리 (7 축)

각 실험에 대해 다음 7 축을 *순서대로* 점검한다.

### A. 실험 환경 한계 (Environment)
- *Docker / Testcontainers 버전, MySQL 버전, OS, JVM* 이 prod 와 정합한가?
- *autoCommit / isolation level / transaction boundary* 가 운영 코드 (Hibernate flush mode 등) 와 일치하는가?
- *connection pool / timeout / driver hint* 가 운영 설정과 어긋나지 않는가?
- → 어긋남 발견 시: *환경 동기화 후 재실험* 권장

### B. 시나리오 한계 (Scenario)
- 시나리오가 *가설을 반증할 수 있는 형태* 인가? (가설 confirm 만 되는 시나리오는 *유의성 부족*)
- *경계 케이스* (각 일자 다른 가용 수 / 다른 row 수 / 다른 thread 수) 를 다루는가?
- *prod 워크로드* 의 RPS / contention 분포와 정합한가?
- → 한계 발견 시: *경계 시나리오 추가 실험* 권장

### C. 측정 도구 의미론 (Tool Semantics)
- *측정 도구* (raw JDBC vs Hibernate vs JPA proxy vs k6) 가 *운영 코드의 의미론* 과 일치하는가?
- 예: JDBC `setReadOnly(true)` 와 Hibernate `@Transactional(readOnly=true)` 는 *완전히 다른 메커니즘*.
- → 어긋남 발견 시: *운영 도구 (Spring Boot Test 등) 로 재실험* 권장

### D. 코드 라벨링 / 분류 버그 (Labeling Bug)
- outcomes 분류가 *실제 동작* 과 일치하는가? (예: catch block 에서 success 로 잘못 분류)
- assertion 이 실제로 의미 있는 검증을 하는가? (true 만 검사하면 의미 X)
- → 발견 시: *코드 수정 + 재실행*

### E. 측정값 해석 오류 (Interpretation Error)
- 박제된 *판정* 이 측정 raw 와 정합한가?
- *원인 분석* 이 충분한가? (예: latency 9_823ms 의 원인이 lock_wait_timeout 인지 pool exhaustion 인지)
- 가설과 어긋난 측정값을 *어떻게 해석* 했는가? (E-4 의 outside insert 차단 같이)
- → 오류 발견 시: *재해석 + 박제 갱신*

### F. 통계적 유의성 부족 (Statistical Power)
- 라운드 수 / thread 수 / 측정 횟수가 *결정에 충분한* 분포를 만드는가?
- *outlier* 가 평균 / p95 를 왜곡하는가?
- *cold cache / warm-up* 영향이 측정에 끼어들지 않는가?
- → 부족 시: *반복 횟수 증가 + 재실행*

### G. 가설 자체 오류 (Hypothesis Bug)
- 가설이 *측정으로 답할 수 없는 형태* 가 아닌가? (예: "사용자에게 좋다" 는 측정 불가)
- 가설이 *암묵적 전제* 를 깔고 있는가? (예: "autoCommit=true 라도 낙관적 락이 작동" — 전제 자체 오류)
- → 발견 시: *가설 수정 + 재설계*

## 3. 재귀 절차

```
Round 1:
  - 8 실험 (또는 N 실험) 박제 읽기
  - 각 실험에 대해 A~G 축 점검
  - 발견된 허점 분류:
    (a) 즉시 수정 가능 (라벨링 버그 / 해석 오류) → 박제 갱신
    (b) 재실험 필요 (환경 / 시나리오 / 도구 의미론) → 재실험 코드 작성 + 실행
    (c) 영구 한계 (측정 도구의 본질적 한계 — 예: Hibernate readOnly 가 raw JDBC 로 재현 불가) → 박제에 *한계* 명시
  - Round 1 결과 박제

Round 2 (Round 1 에서 (b) 가 있을 때만):
  - Round 1 의 재실험 결과를 박제
  - 재실험 결과 자체를 다시 A~G 축으로 점검
  - 발견된 추가 허점 분류
  - Round 2 결과 박제

Round 3 (Round 2 에서 (b) 가 있을 때만):
  - Round 2 의 재실험 결과를 박제
  - 같은 방식 점검

종료 조건:
  - 모든 허점이 (a) 또는 (c) 로 분류됨 → PASS
  - 3 회 재귀 완료 → 남은 허점은 *영구 한계* 로 강제 박제하고 종료
  - 단순 typo / 명시적 중단 — 사용자 결정으로 종료
```

## 4. 박제 형식

각 라운드의 결과를 박제 파일 (예: `documents/feature/{topic}/experiments-results.md`) 의 *별도 섹션* 에
누적 추가:

```markdown
## 재귀 검토 — Round {N} ({YYYY-MM-DD})

### 발견된 허점

| 실험 | 카테고리 (A~G) | 허점 | 분류 |
|---|---|---|---|
| E-{n} | {축} | {구체 허점 설명} | (a) 즉시 수정 / (b) 재실험 / (c) 영구 한계 |

### 즉시 수정된 박제

- E-{n} {축} : {갱신 내용}

### 재실험 결과

| 실험 | 새 가설 / 새 시나리오 | 새 측정 raw | 새 판정 |
|---|---|---|---|
| E-{n}-r{N} | ... | ... | ... |

### 영구 한계 박제

- E-{n} {축} : {왜 본 라운드 / 본 도구로는 측정 불가능한가 + 미래 어떤 환경에서 재현 가능한가}

### Round {N} 종료 조건
- (a) {개수} 즉시 수정 — 박제 갱신
- (b) {개수} 재실험 권장 → Round {N+1} 진행 / 또는 종료
- (c) {개수} 영구 한계 — 박제에 명시
```

## 5. 절차

1. **박제 파일 읽기.** 입력 위치의 박제 결과를 *모든 실험* (E-1 ~ E-N) 에 대해 읽는다.

2. **A~G 7 축 순서 점검.** 각 실험에 대해 *순서대로* (A → G) 허점을 찾는다.
   - 환경 (A) 부터 시작 — 환경 어긋남이 있으면 다른 축의 측정이 무의미.
   - 가설 (G) 마지막 — 다른 축이 모두 OK 인데 측정이 어긋나면 가설 자체 의심.

3. **발견된 허점 분류 (a/b/c).**
   - *(a) 즉시 수정* — 박제 본문 / 표 / 코드 라벨링 만으로 해결 가능
   - *(b) 재실험* — 새 코드 / 새 환경 / 새 시나리오 필요
   - *(c) 영구 한계* — 본 라운드 / 본 도구로는 측정 불가능 (미래 합류 시점 명시)

4. **(a) 즉시 수정 적용.** 박제 본문을 갱신.

5. **(b) 재실험 작성 + 실행.** 새 실험 코드를 `experiment/` 디렉토리 (gitignored) 에 작성, 실행, 결과 캡처.

6. **(c) 영구 한계 명시.** 박제 본문에 *왜 본 라운드로는 측정 불가능 + 미래 어떤 환경에서 재현 가능* 을 명시.

7. **재귀 라운드 결과 박제.** 위 4 형식으로 누적 추가.

8. **종료 조건 확인.** 모든 허점이 (a) 또는 (c) 거나, 3 회 재귀 완료 → 종료. (b) 가 남았으면 다음 라운드 진행.

9. **실험 코드 정리.** 모든 라운드 종료 후 `experiment/` 디렉토리 *전체 삭제* — CLAUDE.md "실험 테스트"
   step 5 정합. 박제 SSOT 만 git 추적.

## 6. 본 스킬이 *반드시* 검출해야 할 패턴

- **autoCommit=true 환경에서 SELECT-then-UPDATE 측정** — 진짜 single-tx 낙관적 락 의미 X (E-3 패턴)
- **JDBC `setReadOnly(true)` 로 Hibernate readOnly 측정** — 도구 의미론 어긋남 (E-6 패턴)
- **단일 thread 가 *동시 actor* 를 시뮬레이션** — race 자체 X (E-7 패턴)
- **outcomes catch block 에서 success/fail 분류 누락** — 라벨링 버그 (E-1 ATOMIC 패턴)
- **가설 confirm 만 되는 좁은 시나리오** — 반증 가능성 X (E-8 의 마지막 1실 한정)
- **next-key gap lock 의 *예상보다 넓은 supremum* 미분석** — 해석 오류 (E-4 패턴)

## 7. 본 스킬이 *하지 않는 것*

- ❌ 결정의 *옳고 그름* 판단 — 본 스킬은 *측정의 재현 가능성 / 의미 정합성* 만 본다
- ❌ *비즈니스 결정* 검토 — 측정 가능 항목이 본질이 아닌 결정은 본 스킬 영역 X
- ❌ 영구 회귀 가드 테스트 검토 — 그건 `verify-tests` 영역
- ❌ 코드 *기능* 결함 검토 — 그건 `verify-code` 영역
- ❌ 자동 게이트 호출 — 명시 호출 전용

## 8. 산출물 검증 (호출 후 자가 점검)

- [ ] 모든 실험에 대해 A~G 7 축이 *순서대로* 점검됨
- [ ] 발견된 허점이 (a)/(b)/(c) 로 *반드시* 분류됨 (애매한 분류 X)
- [ ] (a) 즉시 수정이 박제 본문에 반영됨
- [ ] (b) 재실험이 *실제로 실행* 되어 raw 측정이 박제됨 (시뮬레이션 X)
- [ ] (c) 영구 한계가 *왜 본 라운드 / 본 도구로 측정 불가능* + *미래 어떤 환경* 명시됨
- [ ] 종료 시점에 *남은 허점* 이 모두 (a) 또는 (c) — 또는 3 회 재귀 도달
- [ ] 실험 코드 디렉토리가 정리됨 (CLAUDE.md "실험 테스트" step 5 정합)

## 9. 호출 예시

### 예시 1 — 처음 실험 결과 박제 직후

```
사용자: "실험 8개 다 끝났는데, 결과 한 번 검토해줘. 허점 있으면 재실험까지."
→ Skill(experiment-recurse)
   - 박제 위치 = documents/feature/concurrency-control/experiments-results.md
   - 재귀 한도 = 최대 3
   - Round 1: 7 축 점검 → 허점 발견 + 분류
   - Round 2: Round 1 의 (b) 재실험 → 새 측정 raw
   - Round 3: 필요시 추가
   - 종료 후 정리
```

### 예시 2 — 특정 실험의 가설과 측정값 어긋남 확인 시

```
사용자: "E-4 의 gap insert 가 5/15 도 5초 차단됐어. 가설은 gap 안만 차단인데 — 이거 재검토해줘."
→ Skill(experiment-recurse)
   - 단일 실험 (E-4) 에 7 축 점검 집중
   - 카테고리 E (해석 오류) 또는 B (시나리오 한계) 가능성
   - 재실험 / 박제 갱신
```

## 10. 주의사항

- *재귀 라운드 박제는 누적 추가*. Round 1 결과를 Round 2 가 덮어쓰지 않는다 — 시간축 가시성.
- *재실험 코드는 일회성*. `experiment/` 디렉토리에 두고 박제 후 삭제 (CLAUDE.md step 5).
- *3 회 재귀 도달* 했는데도 (b) 가 남았으면 *영구 한계* 로 강제 분류 — 미래 라운드에 인계.
- 본 스킬은 *측정의 재현 가능성* 이 본질. *결정 자체* 는 사용자 / 시니어 영역.
